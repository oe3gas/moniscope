# BUG-0004: Leeres Stopp-Feld loescht stop_hz und alle Segmente eines Bandes

Gemeldet: 2026-09-23   Schwere: hoch   Status: geschlossen (kein eigener Fehler)
Betroffen: eb200_core/block_admin.py, Bandformular; vermutlich auch Raster und Kanal

## Beobachtung
Wird das Bandformular mit leerem Stopp-Feld gespeichert, verschwinden stop_hz und alle
acht Segmente aus der Katalogdatei. Keine Rueckfrage, keine Meldung, das Formular meldet
Erfolg.

## Reproduktion
git diff -- known_freq/DAB_Band3.json am 2026-09-22 zeigte den Verlust von stop_hz und
aller acht Segmente nach Oeffnen/Speichern des Bandformulars mit leerem Stopp-Feld.
Zurueckgenommen per git checkout.

## Nicht die Ursache
Nicht separat untersucht - Ursache liegt im Formularverhalten selbst, nicht in einem
Anzeigefehler.

## Vermutete Ursache
Das Formular hat Vererbungssemantik - "Leeres Feld = geerbt aus den Datei-defaults".
Fuer Squelch, Demodulation oder Tags ist das richtig. Fuer Bandgrenzen ist es falsch:
ein Band ohne Stoppfrequenz ist ungueltig. Die Segmente haengen an der Bandgrenze und
fallen mit.

Unabhaengig von BUG-0003, wird durch ihn aber ausgeloest: weil die Felder leer
angezeigt werden (siehe BUG-0003), genuegt Oeffnen und Speichern, um Werte zu verlieren,
die man nie angefasst hat.

## Vorbestehend
Ja, wie BUG-0003 (Entscheidungslog-Altfall).

## Folgen
Stiller Datenverlust bei Bandbearbeitung. Vorschlag fuer die Behebung (nicht Teil dieses
Berichts): Pflichtfelder von vererbbaren trennen. Ein leeres Pflichtfeld ist ein
Validierungsfehler, kein Vererbungswunsch. Zusaetzlich erwaegen, ob ein Speichern, das
vorhandene Segmente entfernen wuerde, eine ausdrueckliche Bestaetigung verlangt.

## Abschluss

Geschlossen am 2026-09-23 ohne eigene Behebung. Die vermutete Ursache
(Vererbungssemantik ohne Pflichtfeld-Unterscheidung) hat sich nicht bestaetigt: sowohl
build_band_entry als auch der clientseitige submit-Handler lehnen ein leeres stop_hz
ausdruecklich ab, keiner faellt auf "geerbt" zurueck.

Der beobachtete Datenverlust war ein Symptom von BUG-0003. Die acht Segmentzeilen
entstehen im Browser durch SEG_INIT.forEach(addSegRow); lief das Formularskript nicht,
existierten sie im DOM nicht, und das Formular sendete ein Band ohne Segmente - der
Server hatte nichts zu verwerfen. Der clientseitige Submit-Schutz lag im selben toten
Skriptblock.

Nach Behebung von BUG-0003 empirisch geprueft: Band mit geleertem Stopp speichern ->
Fehlermeldung, git diff leer. Band ohne Aenderung speichern -> git diff leer, alle acht
Segmente erhalten.

Lehre: ein Fehler, der nur zusammen mit einem anderen auftritt, bekommt seine eigene
Nummer - aber die Ursachenanalyse gehoert vor die Behebung. Haette dieser Bericht eine
Validierung ergaenzt, waere sie doppelt gewesen und haette den wahren Grund verdeckt.
